## 1. Who you're working with and what we're building

**The team:** two undergraduate students doing a DBMS Experiential Learning project. Nishanth leads, and the second member's name goes here: `<teammate>`. Both are **new to databases** and are **not yoga or medical experts**. They will be examined in a viva on every design decision, so they must *understand* the work, not just receive it.

**The product:** a safety-aware yoga knowledge base. About 500 practices (asanas, variations, pranayama, mudra, bandha, kriya, meditation) in PostgreSQL, instruction content and practice logs in MongoDB, and a light Python (Streamlit) UI. The headline feature is the **"safe for me"** filter: the user's health conditions are matched against contraindications that each cite a source.

**What matters most, in order:**
1. **Safety data is never silently wrong.** An unsourced or invented contraindication is worse than a missing one.
2. **The students can explain everything.** Clear beats clever.
3. **There is always a working version.** MVP first, then innovations.
4. **The course rubric is fully covered** (see PRD §10).

## 3. Hard rules (never break these)

## 4. How to work: the per-step protocol
For **every** step in WORKFLOW.md:

1. **Orient.** Read the step's Goal, Inputs, Tasks and "Done when". Check section 7 for anything blocking it.
2. **Plan briefly.** Write down the 3–7 things you'll do. If the step involves a design choice, decide it, then write the reason in one or two sentences.
3. **Build in small increments.** Run things as you go. Prefer the simplest thing that meets the acceptance criteria.
4. **Verify against "Done when".** Actually run the checks: execute the SQL, run pytest, load the page. Don't mark a step done on belief. If a check can't be run (for example, no credentials), say so plainly.
5. **Update the docs (mandatory, every step):**
   - section 5 Status Board: update the step's status, date and evidence
   - section 6 Change Log: one row per meaningful change
   - section 8 Improvements Log: if you improvised (see section 4.1)
   - section 7 Open Questions: add, or close with the answer
   - Any affected doc (PRD / ARCHITECTURE / WORKFLOW / data-spec): edit it **and** bump its "Last updated" date. If a design decision changed, add an ADR in ARCHITECTURE §12.
   - The "Current step" line at the top of this file.
6. **Explain to the students.** End every step with a short plain-language summary (see section 9): what was built, the 1–3 DBMS concepts it shows, and what they should be able to answer in the viva.
7. **Suggest a commit.** Give a short commit message that follows H2. Let the students commit unless they've told you to commit yourself.

### 4.1 Improvising (encouraged, with guardrails)
You're expected to use judgement and **improve on this plan** where it's clearly better: tighter constraints, a missing index, a clearer name, a better test case, a simpler implementation, a gap in the safety logic, a rubric item at risk. Don't just follow instructions mechanically.

| Size of change | What to do |
|---|---|
| **Small** (naming, an extra index or test, a refactor inside one module, a better doc wording) | Just do it, then log it in section 8. |
| **Medium** (a new column, changed view logic, a new dependency, moving work between steps) | Do it if it clearly fits the architecture's intent. Log it in section 8 **and** section 6, and update the affected docs. Mention it clearly in your step summary. |
| **Large** (a new or removed table or collection, a changed technology, a changed MVP scope, any change to safety-rule semantics, anything that breaks a frozen gate) | **Propose first.** Write the problem, the options and your recommendation in section 7, and wait for the team's decision. Once approved, record it as an ADR. |

When in doubt about the size, treat it as one size larger.

### 4.2 Judgement and style
- Act when you have enough information. Don't ask questions you can answer from these docs or the code.
- Ask only when the decision really belongs to the team (scope, the safety-rule meaning, anything in the "Large" row).
- Keep code boring and readable: small functions, clear names, comments only where the *why* isn't obvious.
- Prefer SQL that a student can read out loud and explain.
- When something fails, find the root cause before changing things. Don't stack workarounds.
- Report honestly. If tests fail, show the output. If you skipped something, say so.

## 9. How to explain things to the students
- Use plain words first, then the technical term: *"a table that links two others (a **junction table**)"*.
- Use one concrete example from this project: *Headstand + glaucoma*, *Tree Pose variations*.
- Keep it short: 5–10 lines per concept unless they ask for more.
- For each step, finish with **"Viva check"**: 2–3 questions they should now be able to answer, with one-line answers.
- Don't overwhelm. If a step brings in many new concepts, introduce the 2 most important ones and list the rest.

## 10. Technical conventions
| Area | Convention |
|---|---|
| Python | 3.12+, PEP 8, type hints on public functions, `pathlib`, no global state except the connection pools |
| SQL | Keywords in UPPERCASE, identifiers in `snake_case`, singular table names, `id` PK, `<table>_id` FK, one statement per logical block, a comment above each view explaining its rule |
| SQL files | Numbered (`01_`, `02_` …), safe to re-run where possible |
| Mongo | Collections in `snake_case`, fields in `snake_case`, `practice_id` always an int matching Postgres |
| Timestamps | UTC (`timestamptz` in Postgres, ISO dates in Mongo) |
| Encoding | UTF-8 everywhere |
| Tests | `pytest`, under `tests/`, named `test_<module>.py`; the safety matrix lives in `tests/test_safety.py` |
| Branches | `main` is always working. Phase 2 work goes on `feat/<short-name>`. |
| Data | `data/raw/` is never edited by hand. Every transformation is a script. |
| Secrets | `.env` only (git-ignored). |

## 11. Domain cheat sheet (yoga basics for the build)
- **Asana:** a physical posture. **Pranayama:** breath control. **Mudra:** a hand or body gesture. **Bandha:** an energy "lock" (4 main ones). **Kriya:** a cleansing practice (6 classical shatkarma, some with sub-types). **Meditation:** dhyana techniques.
- **Variation:** a modified form of a base pose (half, supported, revolved, bound, wall-assisted). It's stored as a child with `parent_id`.
- **Inversion:** head below the heart (headstand, shoulder stand, and also downward dog to some degree). This is key for glaucoma, hypertension and pregnancy rules. It's modelled as a category.
- **Severity:** `avoid` (don't do it), `modify` (do the adapted version), `caution` (OK with care).
- **Sanskrit transliteration:** IAST uses diacritics (Vṛkṣāsana). `norm_key` strips them so search matches plain spellings.
- **Good free sources:** AYUSH Common Yoga Protocol 2022, Wikipedia List of asanas (CC BY-SA), alexcumplido/yoga-api (MIT, CC0 images), Wikimedia Commons (per-file licence). See RESEARCH.md.
